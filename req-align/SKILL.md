# 模糊需求工程化对齐（req-align）

对齐"我们是不是想做同一个东西"，并把结果沉淀成**可被后续阶段消费的结构化产物**。
本 skill 只做四层链路的第一层，不越界：

```text
需求对齐(req-align) → SDD 规格化 → 架构发现 → 执行计划(execute-plan-plus / orchestrate-plan)
```

## 职责边界

- **做**：定位需求所在层 → 查历史架构决策 → 最少澄清 → 对齐六要素 → 架构边界扫描 → 判定下一阶段 → 落地 `docs/req-align-<yyyy-mm-dd>-<slug>/`（`align.md` + `arch-risk.md` + `acceptance.md`）并追加 `docs/req-align-history/index.md`。
- **不做**：完整 SDD 规格生成（只给模板入口与判定）、架构设计、写代码、拆执行计划。检测到下游工作直接转交对应 skill 或提示用户。

## 核心流程（6 步）

### Step 1 定位需求所在层

判断用户这句话属于哪一层，决定本 skill 是否需要出手：

| 层 | 用户的话 | 动作 |
| --- | --- | --- |
| 需求层 | "我要做一个漫画生成系统" | 本 skill 主场，进入 Step 2 |
| SDD 层 | "角色一致性必须可验证" | 跳过对齐，直接给 `references/templates.md` 的 SDD 模板入口 |
| 架构层 | "用 ScenePlanner Agent + ShotPlanner" | 不做需求对齐，转架构评审（用 codebase-memory `trace_path` 查调用链） |
| 执行层 | "第一步建 domain model" | 已是计划，转 `execute-plan-plus` |

### Step 2 历史架构决策扫描（自动扫 + 按需问）

在澄清之前先看看"这个边界以前是不是已经定过了"，避免重新踩同一个坑或推翻既有决策：

1. 若 `docs/req-align-history/index.md` 存在，用当前需求的关键词 / 模块名做**简单包含匹配**（grep 关键词，不做语义打分）。
2. **无命中** → 直接进 Step 3，不打断用户，也不提这件事。
3. **有命中** → 用 `AskUserQuestion` 问用户是否参考对应 per-run 目录的完整决策（列出命中条目的日期 + 决策摘要供其判断）。
4. 用户选是 → 读取该目录的 `arch-risk.md`（必要时连 `align.md`），把已决议的边界当作本次对齐的既有上下文带入 Step 4 与 Step 5。
5. 用户选否 → 正常继续，不阻塞。

若历史决策与本次需求冲突，**必须在本次 `arch-risk.md` 里显式写明"沿用"还是"覆盖 + 理由"**，不许无声偏离。

### Step 3 澄清（最少问题原则）

只问最高价值的 1-3 个问题（问题清单见 `references/templates.md` §2）：

1. 交付物是什么——系统 / 功能 / 调研 / 修复？
2. 最关键的不变量——哪个环节坏了最致命（角色一致性？数据不丢？时序正确？）
3. 已知边界约束——现有系统依赖、预算、时间、外部 API？

问题能靠上下文推断时就不问。一次最多 3 个，问完即进入 Step 4。

### Step 4 对齐六要素

按 `references/templates.md` §1a 模板输出：

- 🎯 **目标**：一句话复述。
- 📦 **范围**：✅ 支持 / ⛔ 暂不支持——**显式边界是第一条工程沉淀**，"暂不支持"必填，不许空着。
- 🔼 **优先级**：P0 / P1 / P2（Must / Should / Could）。
- ✅ **验收标准**：每条以"输入 X → 输出/行为 Y"表述，**可观察、可验证**。禁止"要好 / 稳定 / 正常 / 流畅"这类不可观察词（检查表见 `references/templates.md` §4）。
- 🧱 **架构边界风险**：见 Step 5，正文落在 `arch-risk.md`。
- ➡️ **下一阶段判定**：见 Step 6。

### Step 5 架构边界扫描

问"这个需求触碰了哪些系统边界？"，按 `references/risk-patterns.md` §2 清单逐项过：

1. 数据流边界：谁生产、谁消费、数据契约是什么。
2. 时序 / 事件流：SSE、消息、异步回调——时序类 bug 高发区。
3. 跨服务 / 跨模块调用：隐含依赖、循环依赖、分层是否正确。
4. 持久化与领域模型：模型歧义 → 后期大重构。
5. 多 Agent / 外部 API 契约：API 理解不足 → 用错或用偏。

命中的边界只**标记风险 + 建议验证阶段**，不在此解决。判据：这条需求未来最可能"需求正确、代码正确、但架构边界错误"的点在哪。

补充规则：

- 逐项过完清单后，**未命中的边界也要在扫描表里写一行**（写"未命中"），证明扫过而非漏扫。
- 若 Step 2 命中的历史决策里已有该边界的决议，**直接引用决议**而非重新判定风险；要推翻它必须写明覆盖理由。

### Step 6 判定下一阶段 + 落地

| 判定 | 条件 | 去向 |
| --- | --- | --- |
| 直接推进 | 验收可观察 + 无高危边界 | 架构发现 / 执行计划 |
| 需 SDD 深化 | 存在"机器和测试可验证"缺口（如角色一致性） | `references/templates.md` §3 SDD 模板（Given/When/Then） |
| 先做架构发现 | 存在高危边界（事件流 / 跨服务契约不明） | codebase-memory `trace_path` 查真实调用链 |

落地产物（目录形态与 `docs/exec-plan-*/` 同构，供后续阶段消费）：

```text
docs/
├── req-align-history/
│   └── index.md        # 跨需求的架构决策索引：只存摘要 + 链接
└── req-align-<yyyy-mm-dd>-<slug>/
    ├── align.md        # 六要素对齐文档（模板 §1a）
    ├── arch-risk.md    # 边界风险扫描 + 决议记录，append-only（模板 §1b）
    └── acceptance.md   # 人工验收勾选清单（模板 §1c）
```

落盘规则：

1. 先输出六要素摘要到对话，**用户确认后**才写文件。用户只要对话结果时，不落文件。
2. slug 用小写字母 / 数字 / 连字符。**目录已存在时绝不覆盖**：改用 `-2`、`-3` 递增后缀，并在对话里说明"检测到同名对齐产物，已新建 xxx"。
3. `acceptance.md` 由 `align.md` 的「✅ 验收标准」提炼成 `- [ ]` 勾选清单——**这是执行完成后人工逐条核对的依据**，首次落盘时全部未勾选是正常状态。
4. 追加一行摘要到 `docs/req-align-history/index.md`（文件不存在则连表头一起创建，模板 §1d）。若该文件存在但格式异常（无表头 / 列数不符），**不阻塞流程**：照常在末尾追加，并提示用户索引需要人工整理。
5. 架构决议是**后续阶段回填**的：架构发现 / 实现阶段验证完一条边界后，追加 `###` 决议段到 `arch-risk.md` 并把扫描表状态改为 `已决议`。首次落盘时决议区块为空是正常的。

## 自检

落盘后运行校验脚本，**入参是产物目录**（非零退出码 = 未对齐完，缺项见输出）：

```bash
python3 scripts/check_alignment.py docs/req-align-<yyyy-mm-dd>-<slug>/
```

检出力：

- `align.md`：缺目标 / 缺优先级 / 缺"暂不支持"边界 / 缺下一阶段判定 / 验收缺失或不可观察。
- `arch-risk.md`：缺「🧱 边界风险扫描」小节或扫描表无数据行 / 缺「📌 决议记录」占位标题。
- `acceptance.md`：非 `- [ ]` 勾选格式 / 条目不可观察。

退出码：`0` 全过、`1` 有缺陷、`2` 参数或路径错误（目录不存在，或误传单个 `.md` 文件）。
注意脚本**不校验** checkbox 是否已勾选、也不要求决议记录非空——那是后续阶段的事。
