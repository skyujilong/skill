# 架构边界失败模式与扫描清单（req-align-v2）

## 1. 核心判据

**需求正确 ≠ 代码正确 ≠ 架构边界正确。**

典型事故链：需求对齐只确认了"做什么"，没确认"系统边界怎么切"；实现期需求与代码都对，但分层 / 事件流 / 契约错了 → 后期大重构，成本高于一切。

真实例子（BaseMessage 事件流）：需求（消息流）正确、代码正确，但"谁负责解包 / 谁负责流转"的边界切错。对齐阶段若问过"这条消息流的数据边界在哪、顺序是否敏感"，返工可避免。

## 2. 边界扫描清单（对齐时逐项过，命中即标记风险 + 建议验证阶段）

1. **数据流边界**：生产者 / 消费者是谁？数据结构契约是什么？schema 变更影响哪些方？
2. **时序 / 事件流**：SSE / 消息 / 异步回调；顺序敏感？重放、丢失、乱序会怎样？
3. **跨服务 / 跨模块**：A 调 B 的隐含依赖？循环依赖？分层倒置？
4. **持久化与领域模型**：一个词多义（"角色"是配置还是实体）？模型歧义会在哪爆雷？
5. **多 Agent / 外部 API 契约**：API 入参 / 出参 / 限流 / 错误是否查证过？用框架能力时是否查了当前版本文档（防凭记忆写 API）？
6. **可验证性**：验收能否转成测试断言？不能 → 判定"需 SDD 深化"。

逐项过完后，未命中的边界也在扫描表里占一行（写"未命中"）。这条**只有 WARN 没有 FAIL**：
实测 6 个真实 run 的类别覆盖率约 97%（35/36 槽位），说明它作为"当场写"的散文要求已经有效，
再加硬门禁只是摩擦。允许同义命名（某 run 用「可观测性」代替「可验证性」视为覆盖）。

## 3. 阶段判定规则

| 情况 | 判定 | 依据 |
| --- | --- | --- |
| 验收全可观察 + 无命中边界 | 直接推进 | 风险低，进架构发现 / 执行计划 |
| 存在"要验证但无断言"的项 | 需 SDD 深化 | 把自然语言变 Given/When/Then（templates.md §3） |
| 命中时序 / 跨服务 / 契约类边界 | 先做架构发现 | 用 codebase-memory `trace_path` 查真实调用链再动手 |
| 需求本身是架构层陈述 | 不启动对齐 | 转架构评审 |

## 4. 决议与失效：为什么必须走脚本

这一节解释为什么闭环回写必须走脚本，理由是设计约束而非偏好。

**观察到的规律：当场写的义务能做到 ~97%，事后跨上下文回写的义务只有 ≤8%。**

| 义务 | 何时执行 | 实测遵守率 |
| --- | --- | --- |
| 扫描表逐项过六类（散文要求） | 写产物时，当场 | 35/36 ≈ 97% |
| mini-plan 记 `Failures: N`（模板槽位） | 写产物时，当场 | 58/58 = 100% |
| **验收清单勾选**（散文要求） | **执行完成后，跨上下文回来** | **5/66 = 7.6%** |
| **风险决议写回**（散文要求） | **架构发现 / 实现后，跨上下文回来** | 决议段写了但状态列未同步；覆盖标记 0/1 |

机制：跨上下文边界后，事后义务**没有任何触发点**。加粗、写两遍、附理由都不产生触发点。

所以下面三件事不靠自觉，靠脚本：

| 动作 | 命令 | 脚本保证了什么 |
| --- | --- | --- |
| 决议一条风险 | `align_state.py resolve-risk` | 同一次原子写里改状态列 + 追加决议段，两处不可能不一致 |
| 勾选一条验收 | `align_state.py close-ac --evidence` | 证据非空；且下游 `complate` 以此为前置条件，义务从"事后"变"当场" |
| 覆盖一条边界 | `boundary_state.py supersede` | 同时改台账两行 + 给旧 run 插失效横幅 + 更新时间线 |

**禁止手改** `arch-risk.md` 的状态列、`acceptance.md` 的 checkbox、`boundaries.md` 的任何一行。
手改会绕过原子性，导致状态列与决议段漂移。

## 5. 边界沉淀与失效

- **一条边界结论确认后进台账**（`boundary_state.py add`），一行一条决策、单句结论、以模块为主键。
  以模块为主键才能按关键词检索"模块 X 的边界现在是什么"；run 为主键的长句摘要检索不出结果。
- **生命周期只有两态**：`生效` / `已被覆盖`。没有"待定"——待定的东西不该进台账。
- **覆盖必须双向可见**。如果只在台账里标记覆盖、不在旧 run 里留横幅，被覆盖的旧决议仍自称生效；
  而项目 `AGENTS.md` 又把整个 `docs/req-align-*/` 列为事实来源、不区分失效
  → 下次扫描会同时命中失效与生效两条决议。`supersede` 一条命令完成双向标记；
  `check_alignment.py` 会把漏掉的横幅报成 FAIL。
- **踩坑挂在边界上**（`boundary_state.py pitfall-add`），下次 `scan` 命中该边界时自动带出。
  只写不读的教训等于没写。

## 6. 对齐产物质量自检

跑 `check_alignment.py <run_dir>`；下面是它会检出的东西，不必人工逐条核对：

- 「⛔ 暂不支持」为空 / 验收缺输入输出或含不可观察词
- AC-N / RISK-N 缺失、重复、形态非法
- `align.md` 与 `acceptance.md` 的 AC 集合不一致
- `handoff.json` 与 Markdown 不同步（提示重跑 `sync`）
- 状态列与决议段不一致（漂移）
- 被覆盖决议缺失效横幅（stale）
- 台账 `被谁覆盖` 指向不存在的 ID

`--strict-closure` 追加：全部 AC 已勾选且带证据、无 `待验证` 遗留。这是 exec-plan 收尾门禁用的模式。
